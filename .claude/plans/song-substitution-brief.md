# Runtime Song Substitution — Concept Brief

## Problem

A real diagnosis (done in this conversation, not speculative) found that ~85% of songs in a real game failed to play with "Embedding disabled by the owner" (YouTube IFrame error 101/150), even though every one of those videos was verified via **both** the YouTube Data API's `status.embeddable` field **and** the oEmbed endpoint to be embeddable. Root cause: many official/label-uploaded music videos restrict embedding to an **approved-domain allowlist** rather than blocking it globally. Neither API reflects per-domain restrictions — that can only be discovered by an actual browser attempting to load the video from the real origin (`setlist.mooseflip.com`), which is exactly what happens (and fails) during a live game. This is a genuine YouTube platform limitation with no offline/pre-check workaround; it can only be handled reactively, at runtime, when a real failure occurs.

## Goal

When a song fails to play mid-game (the receiver's `YT.Player` `onError` fires, exactly as it already does today), the **server** should automatically search for and try up to 2 alternate YouTube videos of the same song (different uploads — e.g. official audio, lyric video, fan upload — which are far less likely to carry the same domain restriction as the official music video) before falling back to today's existing manual host "Skip" flow. This should feel, from the players' perspective, like a brief pause ("finding another version…") rather than a hard failure requiring host intervention every time.

## In scope

- **Trigger**: the existing `reportPlaybackError` flow (receiver → `store.reportPlaybackError()` → Socket.IO → `engine.reportPlaybackError()` in `packages/server/src/engine/engine.ts`) is the entry point. Today this only surfaces the error as a host-facing message with a manual Skip button (see the code around `reportPlaybackError` in `engine.ts` and its handling in `packages/client/src/player/screens.tsx`'s `BuzzScreen`/host controls, and the receiver-side error display in `packages/client/src/receiver/App.tsx`'s `PlayingTV`). This behavior must be extended, not replaced: automatic retry happens first; only after retries are exhausted does today's manual-Skip behavior kick in, unchanged.
- **Alternate video search**: a live call to the **YouTube Data API v3 search endpoint** (`GET https://www.googleapis.com/youtube/v3/search`), made directly from the **Node server** using the existing `YOUTUBE_API_KEY` env var (already present — currently only consumed by the offline Python builder's embeddable pre-check; this is the first live use of it from the Node server). Use Node 24's built-in global `fetch` — no new HTTP client dependency needed (confirmed: `packages/server/package.json` has no axios/node-fetch/undici direct dependency, and none should be added).
- **Retry cap**: try **2** alternate candidates per failed question before giving up and falling back to the existing manual Skip flow. (Decided — not 3.)
- **Same-song verification**: since YouTube search can return unrelated results, each candidate must be checked for plausible title/artist match before being tried (avoid confidently "fixing" a song by playing a completely different one). No text-normalization helper currently exists in this repo (checked: no `normalizeText`/`normalize` utility in `packages/server/src` or `packages/shared/src` — unlike the sibling `pinpoint` project, which has one in `packages/server/src/engine/cards.ts` for a different purpose). The planner should design a lightweight, self-contained matching heuristic (e.g. normalized substring/token-overlap check against the search result's title against the original title+artist) — pull in a real dependency only if there's a strong reason; a hand-rolled normalizer in the ~10-20 line range, consistent with this codebase's general preference for small hand-written logic over new dependencies (see the Python builder's own hand-rolled parsing/validation style for the house preference), is likely sufficient and should be the default assumption.
- **Visible retry state**: while the server is searching for/trying an alternate, the TV and player screens should show a brief "finding another version…"-style indicator (exact wording is the planner/executor's call — match the existing UI voice, e.g. compare `PlayingTV`'s existing `a.playbackError && <div className="sub">⚠️ {a.playbackError}</div>` styling). **Buzzing must stay disabled during the retry window** — nobody should be able to buzz in on a song that isn't actually playing yet. This likely needs a small protocol/state addition so the receiver and players can distinguish "actively retrying" from "playing normally" and from "exhausted retries, host must Skip" — the planner should design the minimal state needed (a new sub-state, a boolean/enum field on the active question, or reuse of an existing field — planner's call, but must not break the existing spectator-safe projection discipline: see `packages/server/src/engine/project.ts`'s header comment on the three secrets and where each is allowed to appear, particularly that the **videoId stays receiver-only** — a retry must not leak candidate video ids to player sockets).
- **Fallback behavior unchanged**: after 2 failed alternates, behavior must be identical to today's existing manual-Skip flow (`skipQuestion`, `reportPlaybackError` host-facing display) — no regression there.
- **Testing**: the live YouTube Data API v3 search call must be **fully mockable/injectable** in the automated test suite, exactly like every other external dependency in this codebase (`ytmusicapi` client injection in the Python builder's `build_bank(client, ...)`, the `ai_client`/`youtube_session` injection pattern in the same file, and the existing `packages/server/src/net/__tests__` Socket.IO integration-test harness pattern). No test may make a real network call or require a real `YOUTUBE_API_KEY`. Since this is server-side TypeScript (not the Python builder), the planner should design the equivalent DI seam for this codebase — likely an injectable fetch-like function or a small client interface passed into wherever the room runtime / net layer is constructed, mirroring how `RoomManager`/`GameEngine` already take injected dependencies (see `packages/server/src/net/rooms.ts`'s `RoomManager` constructor and `GameEngine`'s `EngineDeps`).

## Out of scope

- No changes to the **offline Python builder's** embeddable pre-check (`scripts/questionbank/build_bank.py`) — that stays as-is; this feature is purely a live, runtime mitigation for what that offline check structurally cannot catch.
- No attempt to pre-detect domain-restricted embedding at bank-build time — already established as impossible without a real browser test from the real origin.
- No UI for a host to manually trigger "try an alternate" on demand — this is fully automatic, triggered only by an actual playback failure. (A manual "try another version" host button could be a future enhancement; not part of this feature.)
- No changes to scoring, buzzing race logic, or judging — those are untouched; this only affects what happens between a playback failure and the song either recovering or falling to the existing Skip flow.
- No retry budget/rate-limiting design beyond the per-question cap of 2 — this is not expected to be called often enough within a single game to need its own quota management beyond that cap (YouTube Data API v3 search costs 100 units per call against a 10,000/day default quota — worth a one-line note in the plan's risks section, but not a feature to build guardrails for beyond the existing 2-attempt cap).

## Constraints

- **Runtime-only, TypeScript, Node server.** No Python/ytmusicapi involvement in the live path — that stays exclusively in the offline builder.
- **Reuse `YOUTUBE_API_KEY`** — same env var, same key, no new credential to manage. It is not currently threaded into the Node server's config/env loading at all (check `packages/server/src/env.ts` and wherever `docker-compose.yml`/`.env.example` define server env vars — `YOUTUBE_API_KEY` is currently documented as "Python builder only, not read by the Node server" in both `.env.example` and `README.md`; **this changes with this feature** and those two files need updating to reflect that the Node server now reads it too).
- **Spectator-safety discipline must hold**: videoId stays receiver-only (per the existing three-secrets model in `project.ts`); no candidate/attempted video ids should ever reach player sockets, only the receiver.
- **No client timing/trust**: consistent with the rest of this engine's design (buzz race is server-timestamped, never client-supplied), the retry-attempt sequencing and cap enforcement must live server-side in the engine/net layer, not be driven by client requests.
- **Existing test-suite conventions**: `packages/server/src/engine/__tests__` (pure engine unit tests against injected deps) and `packages/server/src/net/__tests__` (Socket.IO integration tests, see `integration.test.ts` and `race.test.ts` for the harness pattern) are the two test surfaces this feature will need to extend. `npm test` runs both server and client workspaces; `npm run typecheck` covers all three.
- This is a **live, deployed app** at `https://setlist.mooseflip.com` (Docker, `docker compose up -d --build`, `.env`-driven config) — the existing deployment pattern applies unchanged; this feature doesn't need new Docker/Cloudflare work, just a code change + redeploy.

## Acceptance criteria

1. When the receiver reports a playback error (`reportPlaybackError`) for the currently active question, the server automatically searches YouTube Data API v3 for an alternate video of the same song and, if a plausible match is found, tells the receiver to play it — without any host action required.
2. If the first alternate also fails, the server tries **one more** (2 total attempts), then — and only then — falls back to exactly today's existing behavior (host-facing error message + manual Skip button), unchanged.
3. A candidate search result is checked for plausible title/artist similarity to the original song before being tried; a clearly unrelated result (e.g. totally different title) is not played.
4. While a retry is in progress, players cannot buzz in (buzzing stays disabled until the song is actually confirmed playing, or retries are exhausted and the question reverts to the manual-Skip state), and the TV/player screens show some indication a retry is happening rather than looking frozen or silent with no explanation.
5. No candidate or attempted video id is ever sent to a player socket — only the receiver socket, consistent with the existing `receiverPlayback`-is-receiver-only rule.
6. The YouTube Data API v3 search call is fully injectable/mockable; `npm test` (server workspace) passes with new tests covering: a successful first-alternate recovery, a successful second-alternate recovery after the first also fails, exhausting both attempts and falling back to manual Skip, and a search result that's rejected for not plausibly matching the original song — all with zero real network calls and no real `YOUTUBE_API_KEY` required.
7. `npm run typecheck` and the full `npm test` (server + client workspaces) pass with no regressions to existing tests (especially the existing `reportPlaybackError`/Skip-flow tests, if any exist — check `packages/server/src/engine/__tests__` for current coverage of `playbackError` to confirm this feature doesn't silently break it).
8. `.env.example` and `README.md` are updated to reflect that `YOUTUBE_API_KEY` is now also read by the **Node server** at runtime, not just the offline Python builder.

## Open questions & decisions made

- **Plan review**: user chose to **skip** the Phase 3 approval gate — proceed straight from plan to execution after this session's own sanity check.
- **Retry cap**: 2 alternate attempts per failed question, decided.
- **Retry UX**: a visible "finding another version…"-style indicator on TV/player screens during the retry window, with buzzing disabled throughout — decided, not a silent background retry.
- **Still open for the planner to decide and document** (not blocking, but should be resolved explicitly in the plan):
  - Exact search query construction (e.g. `"{title} {artist}"` vs. adding terms like "official audio"/"lyrics" to bias toward embeddable-friendly upload types — worth reasoning about since official-video-style results are the ones most likely to carry the same restriction we're trying to escape).
  - Exact same-song matching heuristic/threshold (a hand-rolled normalizer is the assumed default per the "Constraints" section above; planner should specify the exact algorithm, e.g. lowercase + strip punctuation + token overlap ratio, with a concrete threshold).
  - Exact protocol/state field(s) added to represent "retrying" — planner's call on the minimal-diff design, but must preserve the existing spectator-safety three-secrets model.
  - Whether the two retry attempts are searched for both up front (search once, get 2+ candidates, try them in order) or searched one at a time (search again only if the first attempt fails) — planner should pick one and justify it (searching once for multiple candidates is one fewer live API call in the common case where the first alternate works; searching per-attempt is simpler state to reason about). Lean toward whichever is simpler to implement correctly and test, but state the tradeoff.
